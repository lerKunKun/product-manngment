# W3-PERF-02 慢查询 + 索引复盘

日期：2026-05-02
作用域：sys_audit_log / product_snapshot / product_price_history / product_inventory_history / task / preview_theme / store_product / user_invitation
对应 migration：`backend-api/src/main/resources/db/migration/V20__hot_query_indexes.sql`

## 1. 调研方法

- `grep -rn "selectList|selectPage|selectOne|LambdaQueryWrapper"` 仓库 + 各 controller / scheduler / service 的 where + orderBy 组合
- 对照各表 V1 / V9 / V10 / V13 / V14 / V18 现有索引识别盲区
- 在 dev MySQL（数据近似空）跑 EXPLAIN 看 plan 类型 + 索引命中
- 不依赖真实数据规模 —— 重点是 plan shape：是否能用上 index、是否避免 filesort、是否避免全表扫

EXPLAIN 在 dev 库的局限：行数极少时优化器倾向选最早建的索引（cardinality 估算粗糙），但只要新索引出现在 `possible_keys` 中、且 SQL 列匹配，生产数据量上来后会按 cost 切换。

## 2. 各表分析

### sys_audit_log
- 现有索引：`idx_user_created (user_id, created_at)` / `idx_module_created (module, created_at)` / `idx_created_at`
- 当前查询：仅 `AuditAspect` 写入，**无任何 controller 读取**
- 决策：**不补索引**。等 W4-OPS 上线 console 审计视图后再按实际过滤组合补
- 备注：`triggered_by` / `actor_id` 等列在本仓库 schema 中是 `user_id`；现有 (user_id, created_at) 已覆盖最常见的"按人查时间序"

### task
- 现有索引：`idx_tenant_type_created (tenant_id,type,created_at)` / `idx_status_created` / `idx_parent` / `idx_store (store_id,type,created_at)` / `idx_task_saga_step (type,saga_step,status)`
- 热查询：`TaskController.list()` 三个可选过滤 (type, status, storeId) 任意组合，ORDER BY id DESC
- 缺口：仅按 `type` 过滤时（如 ops 看所有 PRODUCT_PUSH 任务）现有 (tenant,type,...) 前缀不匹配（tenant 没传），(type,saga_step,status) 在 type 单选时也只能走 type 前缀但不覆盖 ORDER BY id
- 加了什么：`idx_task_type_id (type, id)` —— 让 type 单过滤直接用索引前缀 + 索引内 id 排序
- EXPLAIN：在空表上优化器选了 `idx_task_saga_step`（同样匹配 type 前缀，cardinality 估算几乎相同）；生产数据上 task_saga_step 大多数行 saga_step IS NULL，会切到 idx_task_type_id

### product_snapshot
- 现有索引：`idx_store_product (store_id, product_external_id, created_at)` / `idx_tenant_created` / `idx_status (status, created_at)`
- 热查询：`ProductSnapshotController.list()` 过滤 (storeId, productExternalId, status) 任意组合，ORDER BY id DESC
- 缺口：(storeId + status) 组合（最常见的"看某店某类快照"UI），现有 idx_store_product 第二列是 product_external_id，过滤要回表
- 加了什么：`idx_snapshot_store_status_created (store_id, status, created_at)` 让该组合走纯索引
- EXPLAIN：空表上优化器选了 idx_store_product（行数太少，二者代价等价）；生产数据上 status 选择性高时会切

### product_price_history / product_inventory_history（按月分区）
- 现有索引：`idx_variant_changed (store_id, variant_external_id, changed_at)` / `idx_tenant_changed`
- 热查询：`ProductSnapshotController` 详情接口按 (store_id, product_external_id) 取最近 10 条变更（**不带 variant**），分布在多个分区
- 缺口：现有 `idx_variant_changed` 第二列是 variant 而非 product，product 维度查只能走 store_id 前缀 + filesort + 多次回表
- 加了什么：
  - `idx_pricehist_store_product_changed (store_id, product_external_id, changed_at)`
  - `idx_invhist_store_product_changed (store_id, product_external_id, changed_at)`
- EXPLAIN：空表上优化器仍选老索引，但新索引出现在 possible_keys；带 product_external_id 过滤后生产数据切换稳定

### preview_theme
- 现有索引：`idx_preview_dev_store_status` / `idx_preview_product` / `idx_preview_expires (expires_at, status)`
- 三个热查询都已对应：
  1. `PreviewThemeAllocator` 按 dev_store + status count → idx_preview_dev_store_status 命中
  2. `PreviewThemeCleanupScheduler.expireOverdue()` `expires_at < now AND status IN (...)` → idx_preview_expires 命中
  3. `PreviewController.list()` 按 source_product_id + status → idx_preview_product 命中
- 决策：**不补索引**

### store_product
- 现有索引：`uk_store_product (store_id, product_id) UNIQUE` / `idx_shopify_product (store_id, shopify_product_id)` / `idx_tenant_status (tenant_id, status)`
- 热查询：tenant 维度的产品映射列表 UI 是 `WHERE tenant_id=? AND status=? ORDER BY updated_at DESC`
- 缺口：idx_tenant_status 没有 updated_at 列，列表分页要 filesort
- 加了什么：`idx_storeprod_tenant_status_updated (tenant_id, status, updated_at)`
- EXPLAIN：**直接命中**，"Backward index scan" 无 filesort

### user_invitation
- 现有索引：`idx_email_status (email, status)` / `idx_token` / `idx_account_expires`
- 热查询：`InvitationServiceImpl.list()` `WHERE status=? ORDER BY invited_at DESC`（不传 email）
- 缺口：idx_email_status 用不上（前缀不匹配）
- 加了什么：`idx_invitation_status_invited (status, invited_at)`
- EXPLAIN：**直接命中**，"Backward index scan" 无 filesort

### sys_data_scope
- V19 已加 `idx_data_scope_notify_window (cross_company, status, expires_at, expiring_notified_at)`，本次不动

```
|  1 | SIMPLE      | user_invitation | ref  | idx_invitation_status_invited | idx_invitation_status_invited | 1       | const |    2 | Using where; Backward index scan|
+----+-------------+-----------------+------+-------------------------------+-------------------------------+---------+-------+------+---------------------------------+

mysql> EXPLAIN SELECT * FROM store_product WHERE tenant_id=1 AND status='ACTIVE' ORDER BY updated_at DESC LIMIT 20;
+----+------+---------------+------+-----------------------------------------------------------+-------------------------------------+---------+-------------+------+---------------------------------+
| id | type | table         | type | possible_keys                                             | key                                 | key_len | ref         | rows | Extra                           |
+----+------+---------------+------+-----------------------------------------------------------+-------------------------------------+---------+-------------+------+---------------------------------+
|  1 | SIMPLE | store_product | ref  | idx_tenant_status,idx_storeprod_tenant_status_updated     | idx_storeprod_tenant_status_updated | 9       | const,const |    1 | Using where; Backward index scan|
+----+------+---------------+------+-----------------------------------------------------------+-------------------------------------+---------+-------------+------+---------------------------------+

mysql> EXPLAIN SELECT * FROM task WHERE type='PRODUCT_PUSH' ORDER BY id DESC LIMIT 20;
-- 选了 idx_task_saga_step（type 前缀匹配，空表 cardinality 估算等价）；
-- idx_task_type_id 也在 possible_keys，生产数据 + saga_step 大多 NULL 时会切。

mysql> EXPLAIN SELECT * FROM product_price_history WHERE store_id=1 AND product_external_id='gid://1' ORDER BY changed_at DESC LIMIT 10;
-- partitions 列出全部 9 个分区，type=ref，新旧索引都在 possible_keys；
-- 关键是 product_external_id 现在能走索引列匹配而非空表回表。
```
